# ПоРукам — российские B2B-закупки

ПоРукам помогает российским покупателям и производителям согласовать выполнимый заказ: восстановить требования из материалов, найти совместимое производство, подготовить КП, проверить полную стоимость, подтвердить обязательства и учесть исполнение. Совместная закупка и резерв используются там, где совместимы требования и подтверждены условия.

Для понимания пяти пунктов не нужно собирать описание из отдельных приложений. Ссылки на код, тесты и первичные материалы дают возможность проверить утверждения.

Российские компании, русскоязычный интерфейс, расчёты в рублях. Показательные компании, товары, документы и операции синтетические: их нельзя выдавать за реальные продажи, спрос или измеренную экономию. Продукт рассчитан на разные виды бизнеса и множество категорий, без ограничения одной отраслью.

Очередь разработки и статусы хранятся только в [NEXT_STEPS.md](NEXT_STEPS.md). README описывает текущее устройство и границы функций; он не создаёт вторую очередь задач. Подготовка показа, измерения команды и физический стенд находятся в ответственности команды.

## 1. Маркетплейс как среда координации ИИ-агентов

### 1. Задача среды и основания

Сценарии ПоРукам связывают запрос российского покупателя с возможностями российского производителя: требования, минимальную партию, полную рублёвую смету, допуск, согласие и исполнение. [Исследование B01–B13](docs/research/marketplace-pain-points.md) содержит основания проблем; [S16](docs/analysis/stage-16.md) связывает ручные операции с функциями и ограничениями.

| Потребность | Функция среды | Что предъявляем |
|---|---|---|
| B01–B02: требования разрознены или противоречат друг другу | разбор материалов, факты с источниками, уточнение и новая версия | [агенты и результаты](services/llm-gateway/app/agents.py), [контракты S04](docs/architecture/stage-4-agents.md) |
| B03/B06/B10: карточки недостаточно для выбора производства | предметная совместимость, паспорт возможностей и применимый допуск | [правила допуска](services/marketplace/app/category_admission.py), [категории S16](docs/analysis/stage-16-scenarios.md) |
| B04–B05: MOQ и неполная стоимость | совместимая группа, индивидуальная смета и сопоставимая альтернатива | [процесс группы](services/marketplace/app/api/market.py), [методика экономики](docs/analysis/stage-16.md) |
| B07/B11–B12: отказ, доставка и расхождения | ресурсный резерв, варианты замены, фактическая приёмка и ручное решение | [восстановление](services/marketplace/app/api/resilience.py), [исполнение S15](NEXT_STEPS.md#stage-15) |
| B08/B09/B13: рутина и доверие к автоматизации | черновик КП, актуальный спрос, источники, согласие и оценка | [черновик](services/marketplace/app/offer_draft.py), [методика качества](docs/analytics/role-quality-method.md) |

Постоянный поставщик, почта и таблица остаются полноценной альтернативой. В [сценариях S16](docs/analysis/stage-16-scenarios.md) сохранены случаи, где правки, дорогой резерв или переход в новый инструмент дают отрицательный результат. Сценарные параметры не доказывают фактическую экономию, спрос или уникальность на всём рынке.

### 2. Агент предлагает, код считает, человек подтверждает

| Участник | Ответственность | Граница |
|---|---|---|
| LLM через Gateway | извлечение требований и подготовка объяснения/текстового результата | не назначает цену, ресурс, резерв или статус обязательства |
| Обычный код и OR-Tools | предметные проверки, Decimal-суммы, совместимость, распределение, N-1/N-2 и журнал | результат зависит от актуальных входных данных и ограничений |
| Покупатель, продавец, проверяющий | подтверждение спецификации, условий, документов и критичных действий в пределах своих прав | готовность черновика не считается согласием |

Разделение закреплено в [агентах](services/llm-gateway/app/agents.py), [оптимизаторе](services/optimizer/app/solver.py) и [Human Approval Guard](services/marketplace/app/trust.py). Поле без известного основания требует уточнения или ручного ввода; наличие источника само по себе не доказывает правильность значения.

### 3. Роли и исполнители

Роли — функции процесса, а не заявление о семи независимо работающих LLM. [Паспорта ролей](services/llm-gateway/app/role_passports.py) задают разрешённые данные, инструменты, результат и ограничения.

| Роль | Вклад | Исполнитель / доказательство |
|---|---|---|
| Агент требований | текст, PDF, изображения и аудио → факты, источники, конфликты, вопросы | локальная обработка и LLM: [Gateway](services/llm-gateway/app/api.py) |
| Подбор | совместимость потребности с производством и причины отбора | код и объяснение: [agents.py](services/llm-gateway/app/agents.py) |
| Подготовка КП | цена/ступени из каталога, объём из ресурса, срок и источники; неизвестное остаётся открытым | кодовый черновик: [offer_draft.py](services/marketplace/app/offer_draft.py); продавец правит и отправляет |
| Координация группы | совместимость, условия участников, недобор и пересчёт | [market.py](services/marketplace/app/api/market.py), [solver.py](services/optimizer/app/solver.py) |
| Устойчивость | подтверждение резерва и расчёт вариантов отказа/замены | [resilience.py](services/marketplace/app/api/resilience.py); поставщик и покупатель подтверждают критичное |
| Допуск | применимость документов и блокировки обязательств | [category_admission.py](services/marketplace/app/category_admission.py); проверяющий — человек |
| Оценка | телеметрия, исходы процесса и сравнение с экспертным эталоном | [role-quality-2](docs/analytics/role-quality-method.md), [scorecard](services/marketplace/app/api/agent_scorecard.py) |

### 4. Маршрутизация и контракт задачи

[Контракт задачи](services/llm-gateway/app/tasks.py) сохраняет принадлежность компании, роль, вход, ссылки и версии источников, состояние, ревизию, попытки и связанное согласие. Уточнение и продолжение привязаны к текущей версии; раннее или устаревшее действие отклоняется. Повторный запрос не должен создавать второе обязательство — [регрессии жизненного цикла](services/llm-gateway/tests/test_agent_tasks.py).

Трасса должна различать вызов модели, инструмента/расчёта и решение человека. Такой порядок проверяется в [test_tool_registry.py](services/llm-gateway/tests/test_tool_registry.py); конкретный синтетический сквозной материал приведён в [S17](docs/contest/stage-17-evidence.md). Изолированная проверка маршрутизации не является измерением качества живой модели.

### 5. Что видит пользователь

- В запросе и черновике — источники, пробелы и значения для проверки; [интерфейс сценариев](#agent-scenarios).
- Перед обязательством — действующие условия, версию и понятную причину блокировки; [контроль](#safety-and-evaluation).
- В KPI — конверсию допустимых черновиков, фактические правки, раздельные исходы и покрытие телеметрии. Экспертная оценка роли и конверсия процесса имеют разные знаменатели; [методики](docs/analytics/role-quality-method.md).

### 6. Границы и отказ

| Ситуация | Текущее поведение / основание |
|---|---|
| Обязательное локальное извлечение недоступно | результат помечается `failed`, HTTP 503; есть повтор/сохранённый процесс и ручной путь, описанные в [S03–S04](NEXT_STEPS.md#stage-03). Универсального успешного продолжения без модели нет |
| Необязательный внешний review недоступен | консультация пропускается; обязательное локальное извлечение этим не заменяется — [agents.py](services/llm-gateway/app/agents.py) |
| Seller Agent не получает результат модели | отдельный путь `rules_only`; это не гарантия fallback для других ролей — [api.py](services/llm-gateway/app/api.py) |
| Условия, допуск или ресурс не подходят | обязательство блокируется; отсутствие допустимого резерва не превращается в гарантию поставки — [resilience.py](services/marketplace/app/api/resilience.py) |

Из 47 листьев каталога синтетический сквозной путь S15 проверен для всех 46 поддерживаемых; медицинские расходники остаются `unsupported`. Наполнение содержит 101 синтетическую позицию. Предметная экспертиза изделий остаётся отдельным условием; охват профилей и примеров указан в [S16](docs/analysis/stage-16-scenarios.md). Исторические локальные результаты, включая живую модель, относятся к стенду и версиям [S15](NEXT_STEPS.md#stage-15), а не к каждому будущему показу.

<a id="agent-scenarios"></a>
### Формализованные сценарии взаимодействия

Обозначения: **П** — покупатель, **Пр** — продавец, **Атр** — агент требований, **К** — обычный код, **О** — оптимизатор, **ПП** — проверяющий площадки. Роль процесса не означает отдельную LLM.

#### Сценарий 1. Запрос → проверенная спецификация

| Шаг / передача | Вход | Выход | Решение человека |
|---|---|---|---|
| П → Атр через Gateway | текст/материалы, компания, версия источников | сохранённый процесс, факты с локаторами, пробелы и конфликты | П выбирает материалы; внешняя консультация разрешается отдельно |
| Атр → П | факты, вопросы и противоречия | уточнённый результат на текущей версии | П исправляет и разрешает конфликт |
| П → К | актуальный результат и подтверждение | потребность, история версии/согласия | П подтверждает; `ready_for_review` не равно согласию |

Доказательство: [Gateway](services/llm-gateway/app/api.py), [задачи и возобновление](services/llm-gateway/app/tasks.py), [проверки task-contract](services/llm-gateway/tests/test_agent_tasks.py). Непрочитанный источник и сбой модели имеют отдельные исходы; ручная потребность не выдаётся за результат агента.

#### Сценарий 2. Потребность → КП продавца

| Шаг / передача | Вход | Выход | Решение человека |
|---|---|---|---|
| К → Пр | актуальный незакрытый спрос, категория и ограничения производства | запрос и основания соответствия | Пр выбирает, отвечать ли |
| Пр → К | запрос, актуальный товар и ресурсы | черновик цены/объёма/срока с источниками и предупреждениями | — |
| К → Пр | черновик и незаполненные условия | preview/diff после правок | Пр указывает неизвестное и проверяет значения |
| Пр → К | подтверждённые условия | отправленное КП, происхождение черновика и число правок | Пр отправляет |

Доказательство: [offer_draft.py](services/marketplace/app/offer_draft.py), [offers.py](services/marketplace/app/api/offers.py). Логистика и неизвестная цена требуют ручного решения. Полнота черновика и его актуальность проверяются до включения в знаменатель [scorecard](docs/analytics/metric-dictionary.md#scorecard).

#### Сценарий 3. КП → прямое обязательство → исполнение

| Шаг / передача | Вход | Выход | Решение человека |
|---|---|---|---|
| К → П | условия и предметный допуск | выбор или причина блокировки | П выбирает предложение |
| П → К | согласие на текущую версию | сделка, замороженные условия и ресурсный эффект | П подтверждает |
| Пр → К | производство/отгрузка, фактические количества и доказательства | события исполнения | Пр подтверждает свою операцию |
| П → К | получение, расхождение или возврат | подтверждённая приёмка/корректировка и пересчёт | П подтверждает факты; спор требует ручного решения |

Доказательство: [admission.py](services/marketplace/app/admission.py), [trust.py](services/marketplace/app/trust.py), [синтетические сквозные проверки 46 листьев](services/marketplace/tests/test_stage15_acceptance.py). Заказанное, отгруженное, принятое, возвращённое и оплаченное не смешиваются — [словарь метрик](docs/analytics/metric-dictionary.md).

#### Сценарий 4. Несколько запросов → совместимая группа

| Шаг / передача | Вход | Выход | Решение человека |
|---|---|---|---|
| К → О | совместимые версии требований, единицы и MOQ | распределение и смета участников | — |
| Пр → К | условия группы | опубликованное предложение после допуска | Пр подтверждает |
| К → П | индивидуальные суммы, доставка, срок и условия выхода | сопоставимое сравнение либо неизвестная выгода | П проверяет условия |
| Каждый П → К | согласие на текущую версию | соответствующее обязательство | каждый участник подтверждает |
| К → участники при выходе | изменившийся состав | пересчёт, новая версия и необходимые согласия | прежнее согласие не переносится на изменившиеся условия |

Доказательство: [market.py](services/marketplace/app/api/market.py), [solver.py](services/optimizer/app/solver.py), [экономика S16](docs/analysis/stage-16.md). Недобор не создаёт обязательство. Без сопоставимой полной альтернативы процент экономии не вычисляется; положительный эффект группы не обещан заранее.

#### Сценарий 5. Отказ поставщика → проверяемое восстановление

| Шаг / передача | Вход | Выход | Решение человека |
|---|---|---|---|
| К → О | конкретный отказ, доступные мощности, действующие резервы | N-1/N-2, покрытие/непокрытие, стоимость переключения | — |
| К → Пр | условия резервного ресурса и срок действия | подтверждение резерва или отказ | Пр подтверждает |
| К → П | актуальная версия замены, цена и срок | согласованная активация либо блокировка | П подтверждает изменившиеся условия |

Доказательство: [resilience.py](services/marketplace/app/api/resilience.py), [solver.py](services/optimizer/app/solver.py). Истёкший или недопустимый резерв не гарантирует покрытие; стоимость удержания и неизвестная вероятность сохраняются в [S16](docs/analysis/stage-16-scenarios.md).

#### Сценарий 6. Документ → допуск → изменение условий

| Шаг / передача | Вход | Выход | Решение человека |
|---|---|---|---|
| Пр → К | документ, область/назначение и версия | загруженное непроверенное доказательство | Пр заявляет данные |
| ПП → К | файл и предметные требования | подтверждение применимости или отказ | ПП принимает решение |
| К → стороны | срок, отзыв или изменение доказательства | блокировка нового обязательства и уведомление о затронутых условиях | стороны рассматривают действующий процесс |

Доказательство: [documents.py](services/marketplace/app/api/documents.py), [category_admission.py](services/marketplace/app/category_admission.py). Верификация компании не заменяет применимость документа; решение по файлу не является государственной проверкой подлинности.

#### Сценарий 7. Прогон → экспертная проверка → оценка

| Шаг / передача | Вход | Выход | Решение человека |
|---|---|---|---|
| Gateway → К | первоначальный результат, исходы, версии модели/промпта/маршрута | телеметрия и покрытие источников | — |
| Администратор компании → К | подтверждённый эталон, класс задачи и источник | сохранённая экспертная проверка | человек сверяет исходное задание |
| К → пользователь | сопоставимая когорта | полнота/правильность или «Не оценено»; конверсия процесса отдельно | человек решает, что улучшать |

Доказательство: [role-quality-2](docs/analytics/role-quality-method.md), [quality_evidence.py](services/marketplace/app/api/quality_evidence.py). Минимум пять завершённых экспертно проверенных прогонов одной когорты; валидный JSON и согласие пользователя не заменяют правильность. Единого рейтинга агента нет.

#### Отказ и исправление

| Ситуация | Текущее поведение |
|---|---|
| Обязательная локальная модель недоступна | `failed`/503; повтор и ручной путь сохраняют ограничение, автоматический успешный результат не обещается |
| Необязательная внешняя консультация не сработала | review пропускается; локальное извлечение остаётся обязательным |
| Сбой Seller Agent | допустим отдельный `rules_only`; режим не распространяется на все сценарии |
| Некорректная структура ответа | техническая ошибка, а не автоматически подтверждённое поле |
| Пробел/конфликт в прочитанном результате | уточнение или ручная правка; критичный конфликт препятствует согласию |
| Устаревшая версия/чужая компания/повторное согласие | отказ или идемпотентный результат без второго обязательства |

Основания: [Gateway](services/llm-gateway/app/api.py), [task-contract](services/llm-gateway/app/tasks.py), [S03–S04](NEXT_STEPS.md#stage-03). Программные и исторические живые проверки разделены в [S15](NEXT_STEPS.md#stage-15).

#### Связь с интерфейсом и пределами показа

Роли объясняет [«Закупки с ИИ-агентами»](apps/web/app/ai-procurement/page.tsx); источники/правки — кабинет продавца, согласия — таймлайн сделки, оценку — KPI. [S17](docs/contest/stage-17-evidence.md) указывает доказательства этих поверхностей. Синтетический маршрут S15 охватывает 46 поддерживаемых листьев; медицинский лист из меню 47 листьев остаётся `unsupported`; физический микрофон и HTTPS на втором устройстве требуют отдельного прогона.


<a id="business-needs"></a>
## 2. Бизнес-потребности целевых пользователей

**Покупатель** — российская компания из производства, торговли, строительства или сферы услуг, которой нужны товары/материалы с определёнными свойствами, объёмом, сроком, документами и доставкой. **Продавец/производитель** отвечает на запросы, ведёт ассортимент и мощности, подтверждает пригодность и исполняет договорённости. **Редактор площадки** проверяет документы и публикует версии правил категорий; роль назначает администратор, она не выбирается при регистрации.

Главная потребность покупателя — получить сопоставимое и выполнимое предложение. Для поставщика — сократить повторный ввод и обработать актуальный подходящий спрос, сохранив контроль над ценой, ресурсом и обязательствами. Почта, таблица, постоянный поставщик и прямое КП остаются альтернативами: использование платформы не обязано быть выгоднее при любых условиях.

### Полная стоимость, единицы и экономический смысл

- Поддерживаются точные дробные физические объёмы и предметные единицы; денежный расчёт выполняется кодом, не ответом модели.
- Продавец явно задаёт доставку: включена, отдельно с известной суммой либо самовывоз; отдельно указывает налоговую базу. Неизвестные обязательные условия блокируют окончательное согласование.
- Сборы платформы сейчас равны 0 ₽. Дополнительные расходы производителя указываются отдельно. Плата за уже подтверждённое удержание резерва сохраняется понесённым расходом при отмене/замене; возврат — отдельное согласованное действие.
- Процент экономии допустим только относительно сохранённого подтверждённого сопоставимого КП: те же требования, количество, единица, срок, адрес/доставка и налоговая база. Каталожная или предложенная ИИ цена не заменяет это основание.
- Заказ, отгрузка, приёмка, отказ, отмена, возврат и оплата — разные события. Прибыль ограничивается известными затратами и полнотой данных; отсутствие затрат или платёжного источника не означает нулевой расход либо оплату.
- Сценарная экономика учитывает активный ввод, правки, повторы и обучение, отдельно ожидание. Отрицательный эффект и неизвестные данные сохраняются. GMV не является доходом платформы.

Внутренний [анализ S16](docs/analysis/stage-16.md), [12 расчётных сценариев](docs/analysis/stage-16-scenarios.md) и [первичные исследования](docs/research/marketplace-pain-points.md) сохраняют происхождение выводов. Это кабинетное исследование и синтетическая модель, а не подтверждённые пилоты или измерение спроса. Проверяемая польза продукта — конкретный результат маршрута; коммерческий эффект требует фактических исходных данных.

## 3. Архитектура платформы и взаимодействие агентов

### 1. Фактические компоненты

| Компонент | Ответственность | Данные / связи / основание |
|---|---|---|
| `gateway-auth` | пользователи, компании, членство, роли, вход и события безопасности | схема `auth`; [сервис](services/gateway-auth/app), [Compose](infra/docker-compose.yml) |
| `marketplace` | потребности, товары, КП, группы, обязательства, допуск, ресурсный ledger, исполнение и аналитика | схема `marketplace`, явные чтения `auth.*`/`agents.*`; [сервис](services/marketplace/app) |
| `llm-gateway` | обработка материалов, роли, локальная модель, задачи и источники | схема `agents`; [контракт](services/llm-gateway/app/tasks.py), [Gateway API](services/llm-gateway/app/api.py) |
| `optimizer` | ограниченные задачи распределения, групп и N-1/N-2 | OR-Tools, внутренний HTTP-токен; [solver.py](services/optimizer/app/solver.py) |
| Web App | маршруты покупателя/продавца и администратора, исправление/подтверждение | Next.js, React, TypeScript; [apps/web](apps/web) |
| PostgreSQL и MinIO | транзакционные данные и объекты файлов | общий Postgres с тремя схемами, отдельное объектное хранилище; [Compose](infra/docker-compose.yml) |
| HTTPS edge | пользовательский доступ, транспорт и проксирование | отдельный профиль; [HTTPS Compose](infra/docker-compose.https.yml) |

Схемы БД дают организационные границы, но не доказывают физическую изоляцию сервисов. Межсхемные чтения и восстановление общего состояния учитываются в [S15](docs/operations/stage-15.md).

### 2. Потоки данных и решения

1. Покупатель передаёт текст и материалы через Web App в Gateway. Локальная обработка и модель формируют факты/источники; исправленный результат подтверждает покупатель — [api.py](services/llm-gateway/app/api.py).
2. Подбор использует категорию, предметные свойства, паспорт и актуальный допуск. Объяснение не заменяет hard constraints — [agents.py](services/llm-gateway/app/agents.py), [category_admission.py](services/marketplace/app/category_admission.py).
3. Marketplace готовит кодовый черновик КП из каталога и ресурса. Продавец правит неизвестное и отправляет актуальные условия — [offer_draft.py](services/marketplace/app/offer_draft.py), [offers.py](services/marketplace/app/api/offers.py).
4. Группа/резерв используют совместимые версии и ограниченный оптимизатор. Деньги считает обычный код; цена и решение об обязательстве не поступают из LLM — [solver.py](services/optimizer/app/solver.py), [resilience.py](services/marketplace/app/api/resilience.py).
5. Проверяющий решает применимость документа, стороны подтверждают критичные условия; guard, audit и ledger фиксируют результат — [trust.py](services/marketplace/app/trust.py), [S07](docs/architecture/stage-7-trust-control.md).
6. Принятые и возвращённые количества питают коммерческую аналитику, а исходные результаты/эталоны — оценку роли. Это разные измерения — [словарь метрик](docs/analytics/metric-dictionary.md), [role-quality-2](docs/analytics/role-quality-method.md).

### 3. Взаимодействие ролей и состояние

Между вызовами передаются сохранённые артефакты и ссылки, а не свободное разрешение агенту менять сделку. [Паспорта ролей](services/llm-gateway/app/role_passports.py) ограничивают инструменты и данные; [task-contract](services/llm-gateway/app/tasks.py) хранит компанию, ревизию, версии источников, состояния и согласие.

[Проверки задач](services/llm-gateway/tests/test_agent_tasks.py) подтверждают уточнение, восстановление и отказ для устаревшего действия. [Трасса инструмента](services/llm-gateway/tests/test_tool_registry.py) различает модель, расчёт и человека. Эти тесты объясняют устройство среды; они не подтверждают живое качество LLM или внешний A2A-протокол.

### 4. Доверие и внешняя граница

| Механизм | Точное утверждение / ограничение |
|---|---|
| Модель через Gateway | локальные материалы обрабатываются в контуре; секреты задаются вне Git — [hardening](docs/security/hardening.md) |
| Внешняя консультация | только `complex_auto`, отдельное разрешение и ≥3 источников; передаются четыре ограниченных счётчика, без оригиналов и значений фактов — [agents.py](services/llm-gateway/app/agents.py), [S14](docs/architecture/stage-14-integrations.md) |
| Права и обязательства | членство/роль проверяются сервером, критичное требует текущего согласия — [deps.py](services/marketplace/app/deps.py), [trust.py](services/marketplace/app/trust.py) |
| Журнал | hash-chain позволяет проверить связность сохранённых событий; независимого внешнего якоря нет, полная перепись привилегированным администратором не исключена — [S07](docs/architecture/stage-7-trust-control.md) |
| Транспорт | базовый Compose публикует служебные порты на loopback; для второго устройства нужен отдельный доверенный HTTPS-профиль — [S15](docs/operations/stage-15.md) |
| Зависимости | lock-файлы и хеши проверяют выбранные артефакты при установке; отсутствие уязвимостей этим не доказано — [hardening](docs/security/hardening.md) |

Regex-фильтр провайдера не является полной анонимизацией любого текста. Детали механизма, доступа и оценки — в [Приложении 5](#safety-and-evaluation); пентест и юридическая сертификация не заявляются.

### 5. Воспроизводимость и измеренный предел

[S15](NEXT_STEPS.md#stage-15) фиксирует исторический локальный синтетический прогон на MacBook Pro M1 Pro / 16 ГБ: чистые миграции, восстановление PostgreSQL/MinIO на отдельной копии, сохранение историй/approval/ledger и задачи после рестарта. [Инструкция оператора](docs/operations/stage-15.md) задаёт согласованный снимок, отдельное хранение секретов и сверку объектов. Хеш архива проверяет целостность, не подлинность.

В том же историческом прогоне optimizer обработал 20 запросов двух клиентов с 25 поставщиками/100 единицами, p95 около 0,10 с; 26 поставщиков отклонялись с 422. Это конкретный объём, а не промышленный SLO. Снимки памяти и DB-lock не измеряют пик или все виды contention; durable solver-очереди нет. Новый пул, очередь, партиционирование и SSO — возможные решения после измеренного узкого места, а не действующие сервисы.

Физический микрофон, доверие HTTPS и путь обеих ролей на втором устройстве остаются открытыми условиями S15.03. Новый конкурсный стенд требует своей проверки; результаты старой машины ему не приписываются.

### 6. Обоснование технологий

- FastAPI/Pydantic и SQLAlchemy async дают явные серверные контракты и транзакционную работу; версии API и миграции зафиксированы в [архитектурных документах](docs/architecture).
- Decimal и OR-Tools отделяют денежную точность и ограниченное распределение от ответов модели — [словарь метрик](docs/analytics/metric-dictionary.md), [solver.py](services/optimizer/app/solver.py).
- Локальная LLM через Gateway даёт контролируемую границу материалов и сохраняемую телеметрию; обязательный отказ всё равно требует обработки — [S04](docs/architecture/stage-4-agents.md).
- Next.js объединяет два рабочих режима в одном интерфейсе; PostgreSQL/MinIO разделяют транзакционные строки и файлы — [Compose](infra/docker-compose.yml), [восстановление](docs/operations/stage-15.md).

Выбор технологий сам по себе не доказывает рост нагрузки или сокращение затрат.

### 7. Интеграции: выполненное и условные ветки

[S14](docs/architecture/stage-14-integrations.md) сохраняет отдельное решение по каждой ветке:

| Ветка | Текущее состояние |
|---|---|
| Учётная система | версионированный CSV preview/diff/commit/replay с источником; не универсальный коннектор к любой конфигурации |
| ЭДО, реестр, логистика | `not_connected`; известный провайдер не принимает событие (409 без записи). Подпись, государственная проверка и работа перевозчика отсутствуют |
| Внешний поиск/RAG | не подключён без измеренного пробела и разрешённого источника |
| MCP/A2A | сценарий не выбран, реестр внешних адаптеров пуст; подготовленный guard не является исполняемым адаптером и не управляет существующей консультацией DeepSeek |

## 4. Работоспособный прототип и автоматизация поставщика

### 1. Процессы поставщика и проверяемые артефакты

| Процесс | Ручная операция / функция | Артефакт и доказательство | Решение человека |

| КП | повторный ввод цены/объёма/срока → кодовый черновик и preview/diff | [offer_draft.py](services/marketplace/app/offer_draft.py), [offers.py](services/marketplace/app/api/offers.py) | продавец правит и отправляет |

| Каталог | неструктурная карточка → характеристики, единицы, фото и публикация с проверками | [47 профилей](docs/analysis/stage-16-scenarios.md), [46 синтетических сквозных листьев](services/marketplace/tests/test_stage15_acceptance.py) | продавец заполняет, неподтверждённое не публикуется |

| Новый спрос/повтор | ручной поиск и повторный ввод → актуальная лента/rematch и повторный черновик | [B09/S16](docs/analysis/stage-16.md), [приёмка S15](NEXT_STEPS.md#stage-15) | продавец решает отвечать; старое согласие не переносится |

Регионы ограничены российским процессом; географический фильтр не означает автоматически рассчитанный тариф или гарантированную перевозку.

### 3. Разные категории: проверенный объём

Обновлённый синтетический срез [S15](NEXT_STEPS.md#stage-15) охватывает все 46 поддерживаемых рабочих листьев в 12 разделах. Первоначальные девять листьев сохранены в S15 как исторический срез. Медицинские расходники остаются `unsupported`; экспертиза реальных изделий и физический стенд отдельно не подтверждены. [test_stage15_acceptance.py](services/marketplace/tests/test_stage15_acceptance.py) проверяет создание товара/потребности/КП, согласие, чужой доступ, приёмку, ресурс и повтор.

[S16](docs/analysis/stage-16-scenarios.md) различает предметный профиль, допуск и рабочее наполнение. Общий маршрут полезен разным бизнесам, но покрытие конкретной категории требует её доказательств.

### 4. Последовательность показа

1. Покупатель формирует потребность и подтверждает требования; неизвестный параметр остаётся открытым.
2. Продавец выбирает актуальный запрос. Система подставляет известные цену/ресурс/срок из источников; продавец исправляет черновик и указывает логистику.
3. Перед созданием обязательства показываются актуальный допуск и согласие. На отдельном синтетическом случае демонстрируется блокировка неподтверждённого документа.
4. Стороны подтверждают исполнение. Приёмка/возврат пересчитывают коммерческий результат, повтор операции не удваивает его.
5. Отдельный случай показывает недобор группы или недостаточный резерв с объяснением и новыми условиями; выгодный исход не подставляется заранее.
6. В аналитике открываются исходы, источники сумм, правки и покрытие. Экспертная оценка роли появляется только при выполнении методики.

Основание: [формализованные сценарии](#agent-scenarios), [S15](NEXT_STEPS.md#stage-15), [S16](docs/analysis/stage-16.md), [план технического показа](docs/contest/code-review-scenario.md). Эта последовательность — сценарий репетиции, не утверждение, что новое видео уже записано.

### 5. Как измеряется сокращение рутины

Источники в черновике доказывают повторное использование данных, но не измеряют человеко-часы. Scorecard показывает конверсию допустимых черновиков, фактические правки и исходы — [словарь](docs/analytics/metric-dictionary.md#scorecard). Число правок само по себе не доказывает качество модели.

[S16](docs/analysis/stage-16.md) задаёт сопоставимый baseline: активный ввод + исправления + повтор, отдельно обучение и ожидание. [Набор из 12 расчётных сценариев](docs/analysis/stage-16-scenarios.md) сохраняет неизвестные и отрицательные результаты. Его минуты, ставки и рубли — параметры модели команды, а не фактическая экономия поставщиков. Прямой запрос к постоянному поставщику может оказаться дешевле перехода в новый инструмент.

### 6. Сохранённые ручные решения и границы

- LLM не назначает деньги/ресурс и не создаёт обязательство. Продавец задаёт цены и подтверждает актуальные условия — [черновик КП](services/marketplace/app/offer_draft.py).
- Сбой обязательного buyer-extraction даёт `failed`/503 и путь исправления/повтора; `rules_only` Seller Agent и пропуск внешнего review имеют отдельные границы — [Gateway](services/llm-gateway/app/api.py).
- Площадка не является перевозчиком, платёжным агентом или государственным реестром. ЭДО/реестр/логистика остаются `not_connected`; CSV-обмен действует в своём контракте — [S14](docs/architecture/stage-14-integrations.md).
- Зафиксированный платёж и загруженный файл не доказывают банковское исполнение или юридически подписанный документ — [коммерческие метрики](docs/analytics/metric-dictionary.md), [правовые границы](docs/legal/compliance-matrix.md).
- Прибыль выводится только в границах известных сопоставимых затрат; GMV не является доходом платформы — [S16](docs/analysis/stage-16.md).
- Функциональное видео, резерв показа и физические условия конкурсной машины требуют отдельных материалов [S18](NEXT_STEPS.md#stage-18) и [S15.03](NEXT_STEPS.md#stage-15).

### 2. Внешняя приватность: точный состав контекста

Опциональный review получает только четыре вычисленных сервером числовых счётчика:

- `source_count` — до 17;
- `fact_count`, `low_confidence_count`, `repeated_key_count` — до 1000 каждый.

Нужны `complex_auto`, явное `external_context_allowed` и не менее трёх источников. Оригиналы, имена, ID и значения извлечённых фактов в этот контекст не включаются — [agents.py](services/llm-gateway/app/agents.py), [граница S14](docs/architecture/stage-14-integrations.md), [регрессии агентов](services/llm-gateway/tests/test_agents.py). Сбой необязательной консультации не заменяет обязательное локальное извлечение.

Regex-фильтр провайдера является дополнительной проверкой известных форматов, а не полной анонимизацией любого текста. Пустой реестр внешних MCP/A2A-адаптеров и подготовленный guard не являются действующим внешним исполнителем; существующая консультация DeepSeek имеет собственную границу — [S14.04](docs/architecture/stage-14-integrations.md).

### 3. Доверие к компании, товару и операции

| Проверка | Что можно утверждать |

| Компания и документ | верификация компании отделена от предметного допуска товара; актуальный документ проверяется на применимость/срок/версию/отзыв — [category_admission.py](services/marketplace/app/category_admission.py) |
| Решение проверяющего | проверяющий площадки подтверждает применимость загруженного доказательства; это не государственная проверка подлинности — [documents.py](services/marketplace/app/api/documents.py) |
| Чек-лист покупателя | подтверждённые требования и основание доступны в разрешённой поверхности; внутренние данные не открываются автоматически — [допуск](services/marketplace/app/category_admission.py) |

### 4. Контроль действий и аудит

| Контроль | Поведение и доказательство |
|---|---|
| Human Approval Guard | критичное действие требует разрешённого человека и актуальной версии; согласие не возникает из ответа LLM — [trust.py](services/marketplace/app/trust.py) |
| Task-contract | компания, роль, вход, версии источников, ревизия, исход и согласие сохраняются; повтор/возобновление ограничены — [tasks.py](services/llm-gateway/app/tasks.py), [регрессии](services/llm-gateway/tests/test_agent_tasks.py) |
| Запрет модели менять обязательства | цена/ресурс/резерв/статус определяются данными, кодом и человеком — [agents.py](services/llm-gateway/app/agents.py), [offer_draft.py](services/marketplace/app/offer_draft.py) |
| Допуск перед действием | неподтверждённые или устаревшие условия блокируют новое обязательство — [admission.py](services/marketplace/app/admission.py) |
| Источники и правки | черновик сохраняет происхождение; отсутствие данных требует решения человека — [offer_draft.py](services/marketplace/app/offer_draft.py) |
| Раздельные отказы | бизнес-отказ, сбой модели, блокировка допуска/approval и запрет замещения имеют отдельные источники — [scorecard](docs/analytics/metric-dictionary.md#scorecard) |
| Hash-chain | связность и содержимое сохранённого журнала проверяются кодом — [trust.py](services/marketplace/app/trust.py), [S07](docs/architecture/stage-7-trust-control.md) |

Hash-chain выявляет нарушение проверяемой цепочки при изменении записей без согласованного пересчёта. Без независимого внешнего якоря она не исключает полную перепись привилегированным администратором. Append-only история в приложении — правило обычных операций, а не абсолютная неизменяемость внешнего доказательства.

Поведение при отказе зависит от роли: обязательное извлечение даёт `failed`/503 с повтором/ручным путём; Seller Agent может вернуть `rules_only`; необязательный внешний review пропускается — [Gateway API](services/llm-gateway/app/api.py). Универсального fallback нет.

### 5. Оценка: четыре разные группы показателей

| Группа | Источник и знаменатель | Предел вывода |
|---|---|---|
| Кодовые черновики КП | уникальные полные актуальные допустимые черновики; отправленные / допустимые, открытые и исключённые отдельно | конверсия и фактические правки показывают процесс, не правильность LLM — [scorecard](docs/analytics/metric-dictionary.md#scorecard) |
| Качество модельной роли | первоначальный результат и подтверждённый экспертный эталон; критичные признаки эталона | полнота/правильность только для сопоставимой когорты по [role-quality-2](docs/analytics/role-quality-method.md) |
| Телеметрия | известные длительности/стоимости и покрытие; модель, промпт, маршрут, компания и класс задачи | стоимость оценочная, не полный биллинг; неизвестное `null`, не ноль — [role-quality-2](docs/analytics/role-quality-method.md) |
| Коммерческий результат | замороженные условия, фактическая приёмка/возвраты и известные затраты | заказано/исполнено/оплачено отдельно; неполные затраты не дают чистую прибыль — [commercial-analytics-2](docs/analytics/metric-dictionary.md) |

**Методика качества реализована, общего рейтинга агента нет.** Для процентов нужны минимум пять завершённых экспертно проверенных прогонов одной когорты с известными моделью, промптом и маршрутом. Открытые процессы не входят в знаменатель качества; fallback и технический сбой имеют отдельные исходы. Без достаточного основания — «Не оценено».

Администратор компании на KPI сверяет исходное задание, подтверждает эталон/класс/источник; [quality_evidence.py](services/marketplace/app/api/quality_evidence.py) сохраняет evidence. Валидный JSON, согласие пользователя или число свойств не заменяют сравнение с критичными признаками. Повторная проверка одного прогона не увеличивает выборку — [методика](docs/analytics/role-quality-method.md).

### 6. Как проверять результаты

1. Выбрать компанию, окно и сопоставимую когорту; прочитать числитель, знаменатель, исключения и покрытие.
2. Открыть первоначальный результат и подтверждённый эталон; проверить, что поздняя ручная правка не улучшила задним числом ответ модели.
3. Проследить версию источника, решение человека и происхождение обязательства в [трассе S17](docs/contest/stage-17-evidence.md).
4. Для денег сверить согласованное, принятое/возвращённое, затраты и неизвестные платежи; для экономики обратиться к [S16](docs/analysis/stage-16.md).
5. Различать синтетические регрессии, исторические живые проверки S15 и новый показ. Наличие теста в репозитории не означает его запуск в текущей среде.

Параметры 12 расчётных случаев S16 не являются бизнес-метриками клиентов. Исторические smoke локальной модели в [S15](NEXT_STEPS.md#stage-15) не подтверждают качество всех ответов или новый внешний маршрут.

### 7. Открытые границы

- Пентест, юридическая сертификация и доказательство безопасности всех зависимостей не заявлены — [hardening](docs/security/hardening.md), [правовая матрица](docs/legal/compliance-matrix.md).
- Демонстрация использует синтетические компании и документы; реальные персональные данные не нужны — [AGENTS.md](AGENTS.md).
- ЭДО/госреестр/логистика не подключены, внешняя MCP/A2A-совместимость не подтверждена — [S14](docs/architecture/stage-14-integrations.md).
- Качество реальных ответов, фактический выигрыш времени и промышленная нагрузка требуют своих измерений; текущие границы — [S15](NEXT_STEPS.md#stage-15), [S16](docs/analysis/stage-16.md).
- Доверенный HTTPS второго устройства и физический микрофон остаются открытыми; новый стенд проходит отдельную репетицию — [эксплуатация](docs/operations/stage-15.md).

| Среда координации агентов | маршруты buyer/seller, источники, уточнение, инструментальные роли и task-contract | Gateway `test_agent_tasks.py`, `test_tool_registry.py`, `test_stage17_trace.py`; K2 |
| Потребности бизнеса | B01–B13, альтернативы, категорийные сценарии и расчётная экономика | `scripts/test_business_analysis.py`; K1 |
| Архитектура и взаимодействие | четыре FastAPI-сервиса, Next.js, три схемы PostgreSQL, MinIO, OR-Tools и версионные API | миграции и сервисные тесты CI; K3 |
| Рабочий прототип | потребность → товар/КП → согласие → исполнение → аналитика → повтор | `services/marketplace/tests/test_stage15_acceptance.py`; K4, браузерные проверки и сборка |
| Безопасность/доверие/эффективность | область компании, права, документы, approval, audit-chain, ресурсный ledger и экспертные метрики | проверки доступа/конкурентного ресурса/качества, K2–K3 |

Текущий ассортимент содержит **101 синтетическую позицию**, **12 разделов**, **47 предметных листьев**. Синтетические API/DB-проверки охватывают **46 поддерживаемых рабочих листьев**. Медицинские расходники сохраняют `unsupported` с понятной причиной; наличие листа в меню не разрешает медицинское назначение. Первоначальные девять листьев — исторический срез. Программный охват не означает реальную сертификацию изделий или работу внешнего провайдера.

Доказательства лежат отдельно от описания: [очищенная трасса](docs/contest/evidence/stage17-trace.json), [сохранённый машинный отчёт](docs/contest/evidence/stage17-verification.json), [методика воспроизведения](docs/contest/stage-17-evidence.md). Трасса выполняет настоящие HTTP-вызовы ASGI/PostgreSQL, но подменяет ответ LLM. Она проверяет отказы `409`, восстановление и сохранение артефакта, а не качество живой модели.

CI запускает сервисные тесты и миграции, проверяет K1–K4 по JUnit, выполняет проверки интерфейсных состояний и сборку. Хеш JUnit учитывает исходники, предметные данные, миграции, настройки тестов и lock-файлы; неполные наборы категорий, пропуски, ошибки и устаревшие данные не дают успех. Очищенные JSON выгружаются как `stage17-evidence-<SHA>-<attempt>`. Снимок в Git относится к указанному прогону; при изменении реализации нужен новый результат, а не ручное присвоение `passed`.

Карта пяти требований выше не является самооценкой жюри. По сохранённому [положению](Положение%20RLT.StartUp.md) веса K1–K5 — 10/20/15/25/30. K5 не закрывается API-тестом или наличием PPTX. Конкурсные материалы: [презентация](docs/contest/Porukam-pitch.pptx), [точный текст и источники слайдов](docs/contest/pitch-claims.md), [сценарий технического показа](docs/contest/code-review-scenario.md). Организация показа и проверки оборудования — зона команды; статусы не дублируются здесь.

<a id="docker-start"></a>
## Запуск через Docker

Нужны Docker Desktop / Docker Engine с Compose и Python 3 для вспомогательных скриптов. Python 3.14, Node.js и зависимости сервисов устанавливаются в образах; запускать сервисы через локальные `.venv` не требуется.

```bash
python3 scripts/init-local-env.py  # новый .env со случайными секретами, без перезаписи
docker compose --env-file .env -f infra/docker-compose.yml up --build
```

MinIO собирается из исходников фиксированного коммита с проверкой SHA-256, поэтому первый запуск требует загрузки Go-модулей и занимает больше времени. Готовый образ MinIO из удалённого registry не требуется. Происхождение сборки и соответствующие исходники: [infra/minio/README.md](infra/minio/README.md).

Если стенд уже запускался раньше (на компьютере остался том PostgreSQL),
`init-local-env.py` предупредит об этом, а сервисы упадут с
`password authentication failed for user "sborka"`: PostgreSQL применяет
`POSTGRES_PASSWORD` только при первой инициализации тома, и смена `.env` пароль
роли не меняет. Перед запуском выполните один раз:

```bash
python3 scripts/sync-db-password.py   # выставит пароль роли из .env, данные сохранятся
```

Если данные не нужны, вместо этого удалите том (они будут потеряны):

```bash
docker compose --env-file .env -f infra/docker-compose.yml down
docker volume rm infra_postgres_data   # имя тома уточните: docker volume ls | grep postgres
```

Тот же шаг нужен после ротации `POSTGRES_PASSWORD` на существующем стенде;
подробности — в [docs/security/hardening.md](docs/security/hardening.md).

Локальная модель также запускается через Docker. Сохраните следующий дополнительный Compose-файл **вне репозитория**, например `/tmp/porukam-ollama.compose.yml`:

```yaml
services:
  ollama:
    image: ollama/ollama:latest
    restart: unless-stopped
    volumes:
      - porukam_ollama:/root/.ollama
  llm-gateway:
    environment:
      OLLAMA_BASE_URL: http://ollama:11434
volumes:
  porukam_ollama:
```

Запустите тот же проект с дополнением и загрузите модель:

```bash
docker compose --env-file .env -f infra/docker-compose.yml -f /tmp/porukam-ollama.compose.yml up -d --build
docker compose --env-file .env -f infra/docker-compose.yml -f /tmp/porukam-ollama.compose.yml exec ollama ollama pull qwen3.5:9b
```

Ollama и Gateway находятся в общей Docker-сети; порт модели не публикуется на хосте. Сохраняйте оба `-f` при последующих командах обновления этого варианта стенда. Постоянный файл дополнения лучше хранить в операторском каталоге вместо `/tmp`. Для воспроизводимого стенда зафиксируйте проверенный digest образа и версию модели.

Это CPU-режим; на MacBook Docker не использует Apple GPU. Для Linux/Windows с поддерживаемой NVIDIA GPU, драйвером и NVIDIA Container Toolkit в `services.ollama` дополнения задайте `gpus: all`. Сервисы приложения по-прежнему обращаются к модели только через LLM Gateway.

Каталог, ручной ввод и обычные операции маркетплейса не требуют LLM. Маршруты с обязательным извлечением моделью без неё завершаются ограниченной ошибкой; поведение отдельных ролей описано выше. Whisper `small` использует кеш в Docker volume.
Перед первым аудиозапросом подготовьте веса (скачиваются только веса модели,
пользовательские материалы не передаются):

```bash
docker compose -f infra/docker-compose.yml exec llm-gateway python -c 'from faster_whisper.utils import download_model; download_model("small")'
```

Обработчик аудио использует только этот локальный кеш; при отсутствии модели возвращает сообщение о временной недоступности. DeepSeek необязателен: кроме `DEEPSEEK_API_KEY` нужны отдельное разрешение внешнего контекста, `complex_auto` и не менее трёх источников. Передаются только четыре ограниченных числовых счётчика, исходные тексты и значения фактов остаются локальными. Regex не является полной анонимизацией. Ключ нельзя добавлять в Git.
Для Docker адрес Ollama задаётся отдельно как
`OLLAMA_DOCKER_BASE_URL=http://host.docker.internal:11434`.

После запуска:

| Сервис | Адрес | Описание |
| --- | --- | --- |
| Web App | http://localhost:3000 | интерфейс покупателя/производителя/админа |
| Gateway Auth | http://localhost:8001 | аккаунты, вход, компании, проверка (OpenAPI: `/docs`) |
| Marketplace | http://localhost:8002 | каталог, потребности, предложения, сделки, уведомления (OpenAPI: `/docs`) |
| LLM Gateway | http://localhost:8003 | восстановление требований и агенты (OpenAPI: `/docs`) |
| Optimizer | http://localhost:8004 | детерминированные варианты, MOQ, скидки и коалиции (OpenAPI: `/docs`) |
| MinIO | http://localhost:9000 | объектное хранилище файлов (консоль: :9001) |
| PostgreSQL | http://localhost:5433 | БД (внутри Docker — хост `postgres:5432`) |
| pgAdmin | http://localhost:5050 | веб-интерфейс для просмотра локальной PostgreSQL |

В pgAdmin войдите с `PGADMIN_DEFAULT_EMAIL` и `PGADMIN_DEFAULT_PASSWORD` из
локального `.env`. При первом подключении зарегистрируйте сервер с параметрами:
хост `postgres`, порт `5432`, база и пользователь из `POSTGRES_DB` и
`POSTGRES_USER`, пароль из `POSTGRES_PASSWORD`. Данные pgAdmin сохраняются в
Docker volume `pgadmin_data` и не попадают в Git.

Миграции применяются при старте. Демо-аккаунты создаются только при явном
`ENABLE_DEMO_SEED=true`; пароли берутся из локального .env.
Для существующей базы обязательно выполнить [инструкцию смены секретов](docs/security/hardening.md).

### Доступ с других устройств в локальной сети

Базовый Compose доступен только на localhost. Для других устройств включите
[HTTPS-прокси и доверенный сертификат](docs/security/hardening.md).
Прямые API и служебные порты в сеть не публикуйте.

### Демо-аккаунты (синтетические)

| Роль | Email | Пароль |
| --- | --- | --- |
| Администратор | `admin@demo.ru` | `SEED_ADMIN_PASSWORD` из .env |
| Покупатель + продавец (проверенная компания) | `demo@demo.ru` | `SEED_DEMO_PASSWORD` из .env |

<a id="checks"></a>
## Проверки

На macOS и Linux бэкенд можно проверить без работающего стенда, локальных
`.venv`, MinIO и собственного `.env`. Запустите Docker Desktop / Docker Engine:

```bash
docker pull postgres:16.4-alpine   # один раз подготовить образ
python3 scripts/test-backend.py
# Один сервис или отдельный сценарий:
python3 scripts/test-backend.py --service marketplace -- -q tests/test_seed_catalog.py
```

По умолчанию тесты и нативные декодеры выполняются в Linux-контейнерах.
При первом запуске runner собирает отдельный тестовый образ каждого выбранного
сервиса из его `requirements.lock` и версий pytest/pytest-asyncio, используемых CI.
Для первой сборки нужен доступ к реестру образов и пакетам; следующие сборки
используют Docker cache. Образы тестов сохраняются для повторного использования.
Production-образы и зависимости приложения не меняются.

Для каждого сервиса создаётся отдельная закрытая Docker-сеть и временная
PostgreSQL без опубликованных портов, с памятью вместо постоянного тома.
Исходники подключаются только для чтения. В контейнер передаются только временные
ключи и адрес тестовой базы; окружение приложения и smoke-флаги не наследуются; `.env` корня и сервисов
при наличии закрываются пустым файлом внутри тестового контейнера.
Контейнеры и сеть удаляются после проверки, включая сбой или прерывание теста;
сбой тестов даёт ненулевой код возврата. Существующий стенд не изменяется. Для optimizer
база не создаётся. Живая Ollama проверяется отдельно: внешняя сеть тестового
окружения закрыта.


Проверки интерфейса и production-сборка выполняются workflow [CI](.github/workflows/ci.yml); полный повторный обход сайта не требуется для правки документации. Для короткой проверки чистых сценарных расчётов и генератора доказательств:

```bash
python3 -m unittest discover -s scripts -p 'test_business_analysis.py'
python3 -m unittest discover -s scripts -p 'test_contest_evidence.py'
```

Это проверки вспомогательных скриптов, не запуск сервисов вне Docker. Проверки исходников/юнит-тесты не подменяют проверку целого стенда.
