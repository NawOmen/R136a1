# Проверка безопасности «ПоРукам»

Дата: 08.09.2026. База: `main` — `4bb2eba4b24934d44b1df4e60dedc14d27af57a1`, с функциональными изменениями ветки `codex/producer-capabilities-and-buyer-analysis`.

Обновление 10.09.2026: этот документ сохранён как исходный аудит.
Исправления и обязательные действия при развёртывании описаны в [hardening.md](hardening.md).
Ниже статусы относятся к версии на дату аудита, а не к текущему коду.

Проверка исходников приложения, API, конфигурации Compose и CI по 24 парам из файла `fix`. Это статический обзор, не пентест и не гарантия отсутствия других уязвимостей. Состояние реального развёртывания, сетевые правила, внешний мониторинг и настройки GitHub вне репозитория неизвестны. Зависимости Python заданы диапазонами: состав установленных production-контейнеров не подтверждён. Автоматический полный SCA-скан не выполнен. Номера строк относятся к этой версии файлов; диапазоны показывают проверяемый участок.

Найденные проблемы безопасности **не исправлялись**, согласно запросу. Демо-пароли не являются обнаруженной утечкой реальных секретов, но оставлять их в доступном другим людям развёртывании опасно.

## 1. SQL-инъекция

🟢 **1.1. SQL-инъекция — конкатенация строк с пользовательским вводом в SQL:** Уязвимостей не найдено. ORM связывает значения; соседние строковые литералы в `text()` не являются конкатенацией пользовательского ввода. Проверены, в частности, `services/marketplace/app/deps.py:54–63`, `services/gateway-auth/app/api/admin.py:23–27`. Подстановка `%...%` в значение `ilike()` не делает его частью синтаксиса SQL. Динамические DDL в тестах используют созданные программой имена, а не пользовательский ввод.

🟢 **1.2. SQL-инъекция — отсутствие валидации/экранирования перед запросом:** Уязвимостей не найдено. Pydantic проверяет входные модели, ORM/параметры отделяют данные от SQL. Ручное экранирование кавычек поверх параметризации не требуется. Примеры: `services/gateway-auth/app/api/auth.py:46–50`, `services/marketplace/app/deps.py:69–74`. Это не утверждение, что все бизнес-ограничения валидируются идеально.

🟢 **1.3. SQL-инъекция — raw ORM-запросы без binding:** Уязвимостей не найдено. Найденные запросы к данным используют `:uid`, `:cid` и другие параметры; запросы без параметров содержат фиксированный SQL. Примеры: `services/marketplace/app/api/offers.py:42–49`, `services/llm-gateway/app/api.py`, функция `explain_seller_match`; `services/llm-gateway/app/agents.py`, функция `search_capabilities`. Имена полей для SQL из ответа LLM не формируются.

🟢 **1.4. SQL-инъекция — неверная обработка date/datetime:** Уязвимостей не найдено. `services/marketplace/app/schemas.py:179`, `:306`, `:403` используют `date`, выходные временные метки — `datetime`; SQLAlchemy сохраняет типизированные значения. Невозможные календарные даты отклоняет Pydantic. Строки дат не встраиваются в SQL. Проверка «дата не в прошлом» — отдельное бизнес-правило, её отсутствие само по себе не SQL-инъекция.

## 2. Нарушение аутентификации

🟢 **2.1. Аутентификация — открытые пароли или слабый хеш:** Уязвимостей не найдено в хранении пользовательских паролей. `services/gateway-auth/app/security.py:9–16`: bcrypt с солью; `services/gateway-auth/app/api/auth.py:29–34`: в БД записывается хеш. Известные демо-пароли в конфигурации отдельно отмечены в 3.2.

🚨 **2.2. Аутентификация — нет ограничения попыток входа:** В `services/gateway-auth/app/api/auth.py:46–55` неудачная попытка заканчивается 401 без счётчика/задержки/лимитера; в `services/gateway-auth/app/main.py:13–25` соответствующий middleware отсутствует. При доступном API можно неограниченно подбирать пароли и нагружать bcrypt. Сетевой лимитер за пределами репозитория не подтверждён. Направление исправления: лимиты по IP и аккаунту, безопасная задержка и журналирование, без возможности легко заблокировать чужой аккаунт навсегда.

🚨 **2.3. Аутентификация — предсказуемый секрет сессионного токена:** `services/gateway-auth/app/config.py:8`, `services/marketplace/app/config.py:8`, `services/llm-gateway/app/config.py:8`, `infra/docker-compose.yml:36` задают известный fallback-секрет. `services/gateway-auth/app/security.py:20–27` подписывает и проверяет JWT этим секретом. Если переменная окружения не переопределена, знающий секрет может подписать токен для известного UUID пользователя. Наличие UUID и `exp` не компенсирует известный ключ. Требуется обязательный случайный секрет и отказ запуска вне демо при небезопасной конфигурации. Это тот же корневой дефект, что часть 3.2, а не две независимые уязвимости.

## 3. Раскрытие чувствительных данных

🚨 **3.1. Чувствительные данные — HTTP вместо HTTPS:** `infra/docker-compose.yml:45–46`, `:153–155` и `apps/web/app/lib/serviceUrl.ts:1–8` допускают прямой HTTP между браузером и API; TLS-терминация в Compose отсутствует. При использовании HTTP в общей локальной сети логины, пароли и Bearer-токены не защищены шифрованием канала. Loopback-разработка и внутренний healthcheck сами по себе не равны утечке; риск возникает при доступе через сеть без внешнего HTTPS-прокси. Направление исправления: HTTPS для пользовательских запросов и закрытие прямых API-портов от недоверенных сетей.

🚨 **3.2. Чувствительные данные — секреты в коде/открытой конфигурации:** `infra/docker-compose.yml:6`, `:22`, `:36–43`, `:62–63` содержит известные значения по умолчанию для БД, pgAdmin, JWT, демо-аккаунтов и MinIO. Порты БД и pgAdmin публикуются на хосте (`:8–9`, `:23–24`). При запуске без переопределений посторонний с сетевым доступом может использовать эти учётные данные. Реальные API-ключи в проверенных отслеживаемых файлах не найдены. Использование переменных окружения вместо secret manager не автоматически уязвимость; проблема здесь — рабочие общедоступные defaults и отсутствие обязательной безопасной конфигурации. Значения ключей в отчёт не копируются.

🟢 **3.3. Чувствительные данные — пароли/токены/карты в файлах логов:** Уязвимостей не найдено в проверенных явных вызовах журналирования. Данных банковских карт приложение не обрабатывает. Это не проверка фактических логов внешнего прокси и runtime. Отдельный риск: `services/llm-gateway/app/providers.py:76–77` включает текст исключения в `ModelUnavailable`; ошибки модели/валидации могут содержать фрагменты входа. Перед подключением централизованного логирования следует исключить такое содержимое из журналов, а не предполагать, что любой текст исключения безопасен.

## 4. Нарушение контроля доступа

🟢 **4.1. Контроль доступа — проверки только на фронтенде:** Уязвимостей не найдено в проверенных бизнес-операциях. Серверные guards: `services/gateway-auth/app/deps.py:16–63`, `services/marketplace/app/deps.py:21–49`, `:78–120`; проверка администратора в `services/gateway-auth/app/api/admin.py:19`, `:72`, `:108`. Проблема доступного вычислительного API отдельно отмечена в 4.3.

🟢 **4.2. Контроль доступа — IDOR без проверки владельца:** Уязвимостей не найдено в проверенных путях потребностей, предложений, файлов, обращений и агентных запусков. Например, `services/marketplace/app/api/needs.py:176–183`, `:245`, `services/marketplace/app/api/offers.py:38–55`, `services/marketplace/app/api/trust.py:65–72`; в `services/llm-gateway/app/api.py` функции получения/уточнения/подтверждения запуска сверяют `run.user_id` с текущим пользователем. UUID сам по себе не защита: вывод основан на проверках доступа. Публичные обезличенные карточки и опубликованные товары намеренно доступны другим пользователям.

🚨 **4.3. Контроль доступа — отсутствует проверка доступа к вычислительным endpoint:** `services/optimizer/app/main.py:28–45` принимает запросы оптимизации без аутентификации, при этом `infra/docker-compose.yml:77–78` публикует порт сервиса на хосте. Участник доступной сети может обходить Marketplace API и напрямую занимать ресурсы оптимизатора. Изменение чужих сделок этим вызовом не подтверждено: сервис рассчитывает переданные данные. Направление исправления: убрать внешний порт или закрыть его сетью, добавить сервисную аутентификацию и ограничения ресурсов. Для остальных защищённых API права читаются на запросе, а не только при логине.

⚪ **4.4. Контроль доступа — вращаемый CSRF-токен на каждой форме:** Данная уязвимость для проекта не актуальна в указанной формулировке. Текущие защищённые API используют явно добавляемый `Authorization: Bearer`, а не автоматически отправляемую сессионную cookie (`apps/web/app/lib/api.ts:176–185`, `services/gateway-auth/app/deps.py:13–25`). `allow_credentials=False` в `services/gateway-auth/app/main.py:17`. Универсальное требование вращать токен на каждой форме неверно для этой схемы. При переходе на cookie-аутентификацию оценку необходимо повторить; XSS и небезопасный CORS требуют отдельного контроля. Основание: [OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).

## 5. Межсайтовый скриптинг

🟢 **5.1. XSS — пользовательский HTML без экранирования:** Уязвимостей не найдено. В проверенном коде приложения нет `dangerouslySetInnerHTML`, `innerHTML` или `document.write` для пользовательских данных. Тексты товаров, требований и ответов выводятся React как текстовые узлы; новый `apps/web/app/components/CapabilityDescription.tsx` также не интерпретирует HTML. Это не утверждение о безопасности всех транзитивных библиотек.

🟢 **5.2. XSS — URL/куки напрямую вставляются в DOM:** Уязвимостей не найдено в проверенных путях. Поиск кодирует запрос через `encodeURIComponent` (`apps/web/app/components/SiteNavigation.tsx`, функция `search`), отображение идёт через React. Ссылки компаний и товаров строятся по серверным UUID. Хранение токена в localStorage увеличивает последствия возможного XSS, но не доказывает наличие самого XSS.

## 6. Небезопасная десериализация

🟢 **6.1. Десериализация — непроверенный источник объектов:** Уязвимостей не найдено в смысле выполнения произвольных классов/кода при восстановлении объектов. Ответы LLM проходят `json.loads` и Pydantic (`services/llm-gateway/app/providers.py:39–47`, `:75`). PDF/медиа действительно недоверенные и требуют контроля ресурсов/обновления парсеров, но это не найденный вызов небезопасной объектной десериализации.

⚪ **6.2. Десериализация — нет whitelist классов:** Данная уязвимость для проекта не актуальна: внешние данные не выбирают Python/Java-класс для создания. JSON преобразуется в заранее заданные модели Pydantic. Возможность добавить неизвестное JSON-поле не равна возможности инстанцировать произвольный класс.

⚪ **6.3. Десериализация — pickle/Java Serializable для внешних данных:** Данная уязвимость для проекта не актуальна: таких форматов во внешнем API и вызовов `pickle.loads/load`, Java Serializable в проверенном прикладном коде нет. Внутренности библиотек обработки моделей полностью не аудировались.

## 7. Компоненты и анализ кода

🚨 **7.1. Компоненты — нет воспроизводимого процесса проверки/обновления:** `apps/web/package.json:13`, `pnpm-lock.yaml:13–15` фиксируют Next.js 14.2.35. В `.github/workflows/ci.yml:26–32` Python-зависимости устанавливаются из диапазонов `requirements-dev.txt`, включая незалоченные транзитивные зависимости; SCA/security-update шагов в workflow нет. В репозитории нет конфигурации Dependabot/Renovate. Настройки приватного GitHub вне репозитория не проверены. Это установленный пробел процесса, а не доказательство эксплуатации каждой библиотеки. Требуются отдельный план обновления, SCA и воспроизводимая фиксация Python-зависимостей; обновления в этом PR не выполнялись.

🚨 **7.2. Компоненты — неподдерживаемая версия без плана миграции:** `apps/web/package.json:13`, `pnpm-lock.yaml:15`: ветка Next.js 14.x находится вне поддерживаемых версий по [официальной политике Next.js](https://nextjs.org/support-policy). Сам Next.js не заброшен; устарела используемая major-ветка. Нельзя считать её безопасной только потому, что 14.2.35 исправляла отдельные проблемы декабря 2025 года. Необходимо отдельно запланировать переход на поддерживаемую ветку с регрессионными тестами. Полный перечень применимых CVE по фактическому контейнеру этим отчётом не подтверждён.

🚨 **7.3. Компоненты — нет специализированного статического анализа безопасности:** `.github/workflows/ci.yml:26–110` запускает тесты, миграции, TypeScript и проверку русского интерфейса, но не SAST/secret scanning (Bandit, Semgrep, CodeQL или эквивалент). TypeScript — статический анализ типов, поэтому утверждать, что статического анализа вообще нет, было бы неверно. Найден именно пробел security-проверок в версии workflow; отсутствие SAST не является самостоятельным эксплойтом. Внешние проверки GitHub могут быть настроены отдельно.

## 8. Журналирование и мониторинг

🚨 **8.1. Журналирование — отсутствует аудит критичных событий безопасности:** `services/gateway-auth/app/api/auth.py:47–54` не записывает структурированное событие неудачного входа; `services/gateway-auth/app/api/admin.py:104–118` меняет блокировку без события с автором/причиной/прежним значением; `services/gateway-auth/app/deps.py:20–25` возвращает ошибки авторизации без security-событий. Бизнес-аудит существует (`services/marketplace/app/trust.py:40`), история верификации компаний существует — недостаточно именно покрытия событий безопасности. Нужны безопасные события без паролей/токенов с actor, outcome, временем и correlation ID.

🚨 **8.2. Мониторинг — нет алертинга аномалий в поставляемой конфигурации:** `infra/docker-compose.yml:48–54`, `:79–83` содержит healthcheck доступности, но не правила обнаружения перебора/всплесков 401/403 или оповещение оператора. В `infra/` и `.github/workflows/ci.yml` конфигурация такого мониторинга не найдена. Healthcheck и внутренние уведомления о сделках не заменяют security-alerting. Утверждать, что реальная атака уже оставалась незамеченной месяцами, оснований нет. Направление исправления: метрики и централизованный аудит, пороги и проверенный канал оповещения.

## Приоритет дальнейших работ

Перед сетевой демонстрацией: обязательные уникальные секреты/пароли, HTTPS, ограничение прямого доступа к служебным портам, лимиты входа. Затем поддерживаемые зависимости с SCA/SAST, аудит безопасности и алерты. Все изменения — отдельными согласованными задачами; этот отчёт их не выполняет.
