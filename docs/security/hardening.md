# Безопасный запуск «ПоРукам»

Эти изменения исправляют подтверждённые проблемы из [обзора](fix-security-review-2026-09-08.md).
Это не сертификат безопасности и не замена пентесту. Реальные компании и документы в демо не использовать.

## Новый локальный стенд

1. Выполнить из корня репозитория `python3 scripts/init-local-env.py`. Скрипт создаёт
   **новый** `.env` с независимыми случайными ключами и правами 0600; существующий файл не трогает.
2. Для демонстрационных аккаунтов явно поставить `ENABLE_DEMO_SEED=true`.
   Их случайные пароли находятся только в локальном `.env`; фиксированных паролей больше нет.
   После первого запуска вернуть `false`. Регистрация обычных пользователей работает без seed.
3. Запустить `docker compose --env-file .env -f infra/docker-compose.yml up -d --build`.
   Этот вариант доступен **только на компьютере запуска**: http://localhost:3000.
   БД, pgAdmin и API привязаны к 127.0.0.1; оптимизатор не публикует порт вообще.
4. Не коммитить `.env`, сертификаты и приватные ключи. Не отправлять их в чат или в PR.

## Другие устройства и HTTPS

1. Подготовить сертификат для выбранного DNS-имени или IP стенда с SAN,
   доверенный браузерами **всех** участников. Для закрытой сети подходит локальный CA,
   установленный как доверенный на устройствах. Не отключать проверку сертификатов.
2. В каталоге **вне репозитория** разместить `fullchain.pem` и `privkey.pem`;
   ограничить доступ к приватному ключу. Указать абсолютный `TLS_CERT_DIR` в `.env`.
3. Запустить `docker compose --env-file .env -f infra/docker-compose.yml -f infra/docker-compose.https.yml up -d --build`.
4. Открывать именно `https://имя-из-сертификата`. Прокси обслуживает сайт и три API
   на одном origin; браузер не обращается к открытым портам 8001–8003.
   HTTP-вход отвергается. Не открывать служебные порты через firewall/router.

Сертификат, его продление, правила firewall и доверие клиентских устройств —
обязанность оператора. PR не устанавливает сертификат на чужие устройства.
Внутренний трафик Compose остаётся HTTP: это доверенная сеть одного Docker-хоста,
а не конфигурация для распределённого production-кластера.

Прокси принимает до 105 МиБ на маршрутах `/llm/` с запасом на multipart.
API по-прежнему проверяет 25 МиБ на файл и 100 МиБ суммарно для агентной закупки;
у отдельной транскрипции лимит одного файла 25 МиБ. Остальные маршруты прокси
ограничены 26 МиБ. Статика `/_next/static/` не расходует лимиты запросов API,
а страницы и prefetch используют отдельную зону 30 запросов/с с burst 100.

## Обновление существующей базы — без удаления данных

**Не выполнять `down -v` и не удалять тома. Сначала сделать и проверить резервную копию.**

1. Закрыть внешний доступ на время обслуживания.
2. Сгенерировать независимые случайные JWT_SECRET и OPTIMIZER_TOKEN (минимум 48 символов,
   рекомендуется `secrets.token_urlsafe(48)`). Не публиковать вывод. Смена JWT_SECRET
   завершает действие всех прежних токенов: пользователи войдут заново.
3. Смена POSTGRES_PASSWORD в .env **не меняет пароль существующего PostgreSQL**.
   Подключиться локально через `psql`, сменить пароль командой `\password sborka`
   (пароль вводится скрыто), затем обновить .env и DATABASE_URL согласованно.
   Имя роли заменить, если вы используете другое. Проверить подключение до запуска сервисов.
   Автоматизация того же шага: `python3 scripts/sync-db-password.py` — выставляет пароль
   роли из `.env` через локальный unix-сокет контейнера, не удаляя данные. Скрипт
   идемпотентен и ничего не меняет, если тома PostgreSQL ещё нет.
4. Сменить пароль существующего пользователя pgAdmin **в самом pgAdmin**;
   PGADMIN_DEFAULT_PASSWORD применяется к первому созданию, не сбрасывает старый аккаунт.
5. Сменить MinIO root secret в конфигурации сервера и клиентов согласованно, перезапустить,
   проверить загрузку и чтение тестового файла.
6. Уже созданные demo/admin/seller аккаунты не получают новый пароль от seed.
   Сменить их пароли через контролируемую административную процедуру либо заблокировать
   ненужные аккаунты. До этого **не открывать стенд в сеть**. Не оставлять известные пароли.
7. Развернуть обновлённые контейнеры: entrypoint применит миграцию auth/0003.
   Проверить регистрацию, вход, права, каталог и агентную закупку. Не удалять базу ради миграции.

## Что защищено

- JWT: обязательный случайный ключ, только HS256, обязательные sub/exp; неверный UUID даёт 401.
- Вход/регистрация: атомарные счётчики PostgreSQL по аккаунту и прямому peer,
  10/60 попыток в минуту соответственно. Лимит временный, без бессрочной блокировки.
  Прокси отдельно ограничивает реальный клиентский IP, не доверяя переданному X-Forwarded-For.
  За прокси peer-лимит приложения также ограничивает общий поток входа; это осознанный
  предел небольшого стенда, а не настройки масштабного публичного сервиса.
- Оптимизатор: закрытый порт, независимый сервисный ключ, пределы списков, CPU/RAM/PID
  и входящей конкурентности. Ключ оптимизатора не является пользовательским JWT.
- Журнал входов, отказов по лимиту и административных изменений; email/пароли/токены
  и тела запросов не записываются. В журнале есть время, автор действия (если известен)
  и correlation ID. Временные счётчики очищаются при обращениях к авторизации.
- Админ-панель опрашивает журнал каждые 30 секунд и показывает предупреждение о переборе.
  Это проверяемый **внутренний** канал, не обещание круглосуточных SMS/email.
  Оператор должен держать панель открытой или подключить свой сборщик к структурированным
  событиям `porukam.security`. Внешняя доставка уведомлений без настройки не включена.
- Зависимости Python фиксируются в requirements.lock; Docker использует эти файлы.
  Dependabot предлагает обновления; CI проверяет SAST и SCA.
- Next.js переведён с неподдерживаемой 14-й ветки на исправленную 15.5.24,
  совместно с React 19. [Официальный security-релиз от 25.08.2026](https://nextjs.org/blog/august-2026-security-release).
  PostCSS обновлён отдельно по результатам SCA. Внешний вид и бизнес-сценарии не переделывались.

## Регулярные проверки

- Проверять security job и PR обновлений до каждого развёртывания.
- Lock-файлы обновлять через `uv pip compile --python 3.12 --generate-hashes
  --output-file services/ИМЯ/requirements.lock services/ИМЯ/requirements.txt`,
  затем повторять SCA, тесты и сборку. Не замораживать случайный локальный Python 3.14.
- Проверять TLS и доступность стенда со второго устройства; проверять невозможность
  прямого доступа к PostgreSQL, MinIO, pgAdmin и оптимизатору из сети.
- Проверять сигнал: 11 неверных входов на один синтетический email в течение минуты →
  429 и предупреждение администратора. Не запускать нагрузочную проверку на чужой системе.
- Ротация логов Docker ограничена 3 файлами по 10 МБ на сервис.
  Аудит в БД очищается от записей старше 30 дней при обращениях к авторизации;
  при остановленном/неиспользуемом стенде автоматического фонового удаления нет.

## Оставшиеся ограничения

- CSP пока не настроена; её внедрение требует проверки загрузки скриптов Next.js.
- Токен хранится в localStorage. Переход на httpOnly-cookie требует отдельной
  реализации сессионного API и защиты от CSRF.
- Подтверждение email и CAPTCHA отсутствуют; лимиты не исключают распределённую
  массовую регистрацию.
- Вложения потребностей допускают SVG, но выдаются как attachment.
  Не включать inline-выдачу или presigned URL без проверки типов и активного содержимого.
- Документы компаний пока принимают произвольный content_type; перед реализацией
  скачивания нужны allowlist типов и безопасный Content-Disposition.
