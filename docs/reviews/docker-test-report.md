# Автоматическая проверка проекта в Docker

Это **первичный отчёт до исправлений**. Актуальные изменения, повторные проверки и устранение найденных сбоев описаны в [отчёте об исправлениях](docker-fixes.md). Временный MinIO override относится к первичной проверке; текущий Compose включает собственную фиксированную сборку.

## Итог и границы проверки

Проверена реализация из PR #94, исходный коммит `aefeec01c08fbf9e0e7535e7cc86fcc0ab04aa9f`. Все пять образов приложений собраны, отдельный стенд из восьми контейнеров успешно запущен. Проверки обнаружили функциональные ошибки: проект пока нельзя считать полностью готовым.

В этой проверке изменены только автоматические тесты и этот отчёт. Код приложения, зависимости, дизайн и рабочие пользовательские данные не изменялись. Проверка сайта выполнялась headless-тестами, без ручного обхода интерфейса. PR не объединён с основной веткой.

- Production-сборки `gateway-auth`, `marketplace`, `llm-gateway`, `optimizer`, `web`; инфраструктура PostgreSQL, pgAdmin и MinIO. Миграции и синтетическое начальное наполнение выполнены при запуске.

### Ограничение исходного Compose: MinIO

Образ `minio/minio:RELEASE.2024-12-18T13-15-44Z` не удалось скачать: Docker Hub вернул `pull access denied`. Попытка получить ту же версию через Quay завершилась `unauthorized`; архивная ссылка на ARM64-бинарник вернула HTTP 410. Это результаты этого окружения, а не утверждение о доступности образа для всех пользователей.

Для продолжения тестов собран временный образ из официального репозитория MinIO, тег `RELEASE.2024-12-18T13-15-44Z`, коммит `16f8cf1c52f0a77eeb8f7565aaf7f7df12454583`. Использованы Go 1.23, отключённый CGO, Alpine 3.20, сохранена лицензия AGPLv3. Локальный образ `r136-fulltest-minio-source:release`, ID `14d1a7dd1ced5efdda81da3359e5246539aa972fd12690f06e2d2685b3efdb14`, подставлен временным Compose override вне репозитория. Вывод версии бинарника — `DEVELOPMENT.GOGET`, поэтому это сборка исходников указанного коммита, а не проверка идентичности официальному release-бинарнику.

Исходный `infra/docker-compose.yml` не исправлялся. Успешный запуск относится к стенду с этим override. Для воспроизводимой поставки нужно отдельно решить получение фиксированного MinIO-образа, проверить происхождение и лицензию и закрепить доступный digest. Нельзя считать проблему решённой наличием временного локального образа.

### Проверенные сценарии

Существующие backend-наборы запущены целиком. Дополнительные тесты проверяют настоящие сервисы, а не только моки:

- Health и OpenAPI; запрет анонимного доступа к закрытым маршрутам; запись, чтение и удаление уникального синтетического объекта в настоящем MinIO.
- Создание и публикацию потребности, предложение из складского товара, Human Approval Guard при выборе, производство, отгрузку, частичную приёмку, идемпотентный повтор, возврат и подтверждение возврата.
- Финансовый пример: заказано 500 единиц по 5 ₽; принято 300, возвращено 50, чистая приёмка 250, осталось исполнить 200. Выручка 1 250 ₽, себестоимость 750 ₽, валовая прибыль 500 ₽, после прочих затрат 100 ₽ — 400 ₽. Получение денег не подменяется приёмкой: значение оплаты остаётся неизвестным.
- Приватность себестоимости: покупатель не получает внутренние затраты продавца и не может открыть его отчёт.
- Браузерные маршруты покупателя, продавца и администратора, публичные страницы, карточки каталога и компании, профиль производителя, запрет создания потребности продавцом без права покупки.
- Браузерную цепочку выбора предложения, этапов исполнения, приёмки и расчёта прибыли при точной классификации; отдельные регрессии общей категории и ленты подкатегории.

Открытие страницы и отсутствие ошибок не доказывают работу всех её действий. Не выполнялась исчерпывающая матрица всех категорий, каждого сочетания прав и каждой конкурирующей операции; не проводились нагрузочные проверки, платёжные интеграции, ручная визуальная оценка и проверка всех браузеров. Покрытие строк кода не измерялось. Успешные тесты подтверждают перечисленные контракты и сценарии.

## Функциональные ошибки, сохранённые в тестах

### 1. Общая категория из формы не доводится до сделки

Покупатель создаёт потребность «Строительство» с единицами «шт» и резьбой М8. Продавец предлагает подходящий складской болт. При выборе предложения API отвечает HTTP 409: правила зависят от вида товара, требуется подкатегория, без классификации допуск не выдаётся.

Проверены `apps/web/app/needs/new/page.tsx` и `services/marketplace/app/api/offers.py`: форма не предоставляет полноценный путь точной классификации потребности, а `SpecificationCheck` при выборе получает общую категорию. Это незавершённый пользовательский маршрут. Отказ защитного механизма обоснован: нельзя исправлять ошибку отключением проверки допуска.

Нужно согласовать дерево категорий в форме, API и проверке допуска; сохранить точную категорию/подкатегорию и обязательные характеристики, давать понятное объяснение до отправки предложения. После исправления положительный тест общей категории должен проходить без обхода Human Approval Guard. Аналогичные родительские категории требуют отдельных регрессий; их поломка здесь не объявляется доказанной автоматически.

### 2. Лента продавца пропускает запрос в подходящей подкатегории

Запрос с категорией «Крепёж» не появляется у продавца со складским крепежом. В `services/marketplace/app/api/needs.py` фильтр сопоставляет `Need.category` только с `Product.category`, игнорируя `Product.subcategory`. При этом точный запрос и предложение можно связать через API, и межсервисный сценарий доходит до исполнения.

Нужно реализовать согласованное сопоставление дерева и допустимых синонимов категорий для ленты, сохранив проверки видимости и права продавца. Добавить варианты: точная подкатегория, родительская категория, неподходящая категория, несколько товаров и закрытая потребность. Нельзя показывать все запросы без фильтрации ради прохождения теста.

### 3. Список пользователей администратора падает на синтетическом адресе

`GET /api/v1/admin/users` возвращает HTTP 500. Серверная трассировка указывает на `UserOut.model_validate` в `services/gateway-auth/app/api/admin.py`: `EmailStr` не принимает начальный адрес `supplier@porukam.test` с зарезервированным доменом. Интерфейс администратора показывает ошибку загрузки. Остальные проверенные admin-запросы компаний, документов, поддержки и событий безопасности отвечали успешно.

Нужно согласовать синтетическое начальное наполнение с действующим контрактом email и добавить backend-регрессию выдачи всех seeded-пользователей. Проверить миграцию уже созданных синтетических записей. Не ослаблять общую валидацию произвольных email только ради одной fixture.

## Повторный запуск и безопасность тестовых данных

1. Создать отдельный Compose-проект `r136-fulltest`, свободные порты и свежие собственные тома. Не использовать БД с пользовательскими данными. Задать секреты и seed-пароли случайными значениями не короче 16 символов с достаточной энтропией; включить `ENABLE_DEMO_SEED=true`. Env-файл хранить вне Git, с правами 0600. Не печатать развёрнутый Compose-конфиг с секретами.
2. Собрать приложения командой `docker compose --env-file <внешний-env-файл> -p r136-fulltest -f infra/docker-compose.yml build`. Поднять тот же проект с `up -d --wait`. Если исходный MinIO-образ недоступен, стандартный запуск не проходит; использовать явно зафиксированный временный override, описанный выше, и отдельно учитывать это ограничение.
3. Создать отдельные тестовые БД для backend-наборов. В каждом одноразовом контейнере смонтировать весь репозиторий read-only в `/workspace`, выбрать `services/<сервис>` рабочей директорией и передать `TEST_DATABASE_URL` отдельной БД. Установить тестовые зависимости из диапазонов CI и выполнить `pip check`, затем `python -m pytest -q`. Полный путь репозитория нужен для межсервисных fixture. Не направлять эти тесты на seeded-БД браузерного стенда.
4. Для реальной модели повторить `services/llm-gateway/smoke/test_ollama.py` с `RUN_OLLAMA_SMOKE=1`, рабочим адресом Ollama и локальной моделью. Обычный pytest намеренно пропускает эту пару при выключенном флаге.
5. На свежем seeded-стенде запустить весь `tests/e2e`: `pnpm exec playwright test --workers=1`, из этой директории. Передать `E2E_TEST_PROJECT=r136-fulltest`, `E2E_BUYER_PASSWORD`, `E2E_SELLER_PASSWORD`, `E2E_ADMIN_PASSWORD`, соответствующие seed-паролям. Тесты используют localhost:3000/8001/8002 и создают синтетические запросы и сделки. Положительная цепочка предполагает отсутствие старых сделок, поэтому повторный запуск требует свежей основной БД этого отдельного стенда. Не сбрасывать чужую БД.
6. После браузерных сценариев запустить `python -m pytest /workspace/tests/integration -q` внутри одноразового контейнера marketplace в той же Compose-сети. Передать `RUN_DOCKER_INTEGRATION=1`, `DOCKER_TEST_PROJECT=r136-fulltest`, `ENABLE_DEMO_SEED=true`, `E2E_BUYER_PASSWORD`, `E2E_SELLER_PASSWORD`; действующий `DATABASE_URL` должен указывать на `postgres` и `/sborka` именно выделенного проекта. Одного opt-in-флага недостаточно. Запускать последовательно, чтобы межсервисная сделка не нарушала условие свежей БД браузерного теста.
7. Выполнить frontend type-check, проверку русского UI, security-config smoke, Bandit и оба аудита зависимостей. Сохранять JUnit/Playwright-артефакты вне Git: trace может содержать тестовые токены. Не публиковать сырые сетевые трассы.

Новые integration-тесты по умолчанию пропускаются; перед изменением данных требуют явных маркеров стенда. Маркер не заменяет проверку оператором, что он выбрал собственный изолированный проект. MinIO-тест удаляет только созданный им уникальный bucket. Прохождение тестов не является разрешением запускать их на рабочей БД.
