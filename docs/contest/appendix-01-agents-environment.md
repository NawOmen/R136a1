# Приложение 1. Маркетплейс как среда координации ИИ-агентов

> Приложение к презентации «ПоРукам» для конкурса RLT.StartUp (Приложение 1 положения: «концепция маркетплейса как среды координации ИИ-агентов»).

## 1. Задача среды

Малый покупатель и небольшой производитель не могут договориться напрямую не из-за отсутствия товара, а из-за несогласованных требований, минимальной партии и неподтверждённых возможностей производства. Среда агентов нужна, чтобы:

- превратить свободный текст запроса в проверяемую спецификацию с источниками;
- сопоставить спецификацию с подтверждёнными возможностями производства, а не с карточкой товара;
- собрать совместимый спрос нескольких покупателей до минимальной партии;
- подготовить продавцу черновик предложения по данным, а не по догадке;
- удержать исполнение: допуск, резерв и восстановление при отказе поставщика.

## 2. Принцип разделения: агент предлагает, код считает, человек подтверждает

| Слой | Что делает | Чего не делает |
|---|---|---|
| Агент (LLM) | разбирает материалы, извлекает факты, объясняет совпадения и различия, готовит черновики и тексты | не назначает цену, мощность, резерв и не меняет статус сделки; не подтверждает документы |
| Сервисы на обычном коде | расчёты стоимости, объединения, N-1/N-2, допуска, прав доступа, журналов | не интерпретирует свободный текст вместо агента |
| Человек | подтверждает спецификацию, цену, объём, срок, допуск, обязательства | не выполняет ручную работу, которую уже сделала система |

Такое разделение даёт проверяемость: любое существенное утверждение имеет источник, а критичное действие — запись в журнале и подтверждение человека.

## 3. Роли в среде

- **Агент требований (покупатель).** Разбирает текст, файлы, фотографии и голос; собирает характеристики, фиксирует конфликты и задаёт уточняющие вопросы. Покупатель подтверждает карточку потребности.
- **Агент подбора.** Ищет производство по паспорту возможностей, объясняет, почему производитель подходит или нет, показывает отсутствующие данные.
- **Агент предложения (продавец).** Готовит черновик коммерческого предложения: цена и ступени из каталога, доступный объём из остатка склада или календаря мощностей, срок из товара. Каждое поле сопровождается источником; логистику и спорные значения указывает человек.
- **Координатор объединения.** Считает совместимость запросов и выгоду каждого участника, готовит групповое предложение и следит за согласиями.
- **Оптимизатор устойчивости.** Считает последствия отказа поставщика, стоимость резерва и план восстановления.
- **Проверяющий площадки.** Подтверждает документы и их применимость к товару, ведёт допуск и историю решений.
- **Наблюдатель (оценка эффективности).** Считает конверсию сценариев, правки человека, отказы модели и стоимость инференса — см. `docs/contest/appendix-05-security-trust-evaluation.md`.

## 4. Маршрутизация задач

Каждый шаг сценария — задача с типом и исполнителем:

| Тип задачи | Исполнитель | Результат |
|---|---|---|
| Разбор требований из материалов | LLM через LLM Gateway | факты с источниками, список пробелов |
| Проверка возможностей производства | обычный код по паспорту и каталогу | список подходящих компаний с причинами |
| Расчёт цены, объёма, ступеней | обычный код | значения с источником |
| Проверка допуска и документов | код + проверяющий человек | подтверждение или блокировка с объяснением |
| Объединение спроса и расчёт выгоды | OR-Tools | варианты и вклад каждого участника |
| Резерв и восстановление | OR-Tools + подтверждение поставщика | подтверждённый резерв либо честный отказ |
| Объяснение результата | LLM через LLM Gateway | текст на русском без обещаний гарантий |

Правила маршрутизации: если для шага достаточно данных и арифметики — работает код; если нужен разбор неструктурированного текста или объяснение — работает агент; если шаг создаёт обязательство — обязательна точка подтверждения человеком.

## 5. Что видит пользователь

- источник каждого существенного поля (каталог, паспорт, календарь мощностей, требования покупателя);
- пометку «решение человека» там, где система не имеет данных: логистика, спорные характеристики, цена при отсутствии товара;
- объяснение блокировки: почему публикация, сделка или резерв не проходят;
- панель оценки агентов: конверсия, правки человека, отказы модели, стоимость инференса.

## 6. Границы среды

- LLM не принимает финансовых обязательств и не выставляет цену.
- Агент не заменяет юридическую проверку и не выдаёт допуск.
- Отсутствующие данные не додумываются: они помечаются как пробел.
- При недоступности модели сценарий продолжается на правилах, а не останавливается (см. `docs/architecture/stage-4-agents.md`).
