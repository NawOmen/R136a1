## 1. Сервисы

| Сервис | Назначение | Технологии | Ключевые связи |
|---|---|---|---|
| `gateway-auth` | пользователи, компании, роли и права, верификация компаний, события безопасности | FastAPI, SQLAlchemy 2.0 async, схема `auth` | вызывается Web App и всеми сервисами для проверки членства |
| `marketplace` | потребности, каталог, предложения, черновики КП, коалиции, сделки, допуск, резерв, аудит | FastAPI, схема `marketplace` | читает `auth.*` и `agents.*`; вызывает оптимизатор |
| `llm-gateway` | единая точка вызова моделей, агенты, извлечение фактов, объяснения, транскрипция | FastAPI, схема `agents` | единственный сервис, обращающийся к локальной модели |
| `optimizer` | расчёты объединения, распределения объёма, N-1/N-2, стоимости резерва | FastAPI, OR-Tools | вызывается маркетплейсом по внутреннему токену |
| Web App | интерфейсы покупателя, продавца, администратора и площадки | Next.js, React, TypeScript | обращается к сервисам через API |

Данные разделены по схемам; кросс-схемные чтения выполняются явными SQL-запросами, чтобы границы сервисов оставались видимыми.

## 2. Потоки данных

1. **Требования.** Покупатель загружает текст, файлы, фото и голос → Web App → `llm-gateway` (агент требований) → факты с источниками → `marketplace` сохраняет карточку потребности.
2. **Подбор.** `marketplace` сопоставляет требования с паспортами возможностей и каталогом; `llm-gateway` объясняет результат.
3. **Черновик КП.** `marketplace` считает значения из каталога, остатка склада и календаря мощностей (`offer_draft.py`) и сохраняет черновик с источниками полей; продавец подтверждает.
4. **Объединение.** `marketplace` проверяет совместимость запросов и вызывает `optimizer` для распределения объёма и расчёта выгоды.
5. **Допуск.** `marketplace` проверяет документы и их применимость; решение принимает проверяющий площадки; снимок допуска пишется в журнал.
6. **Исполнение.** Таймлайн сделки, резерв, сценарии отказа и восстановление; каждое обязательство проходит Human Approval Guard.
7. **Наблюдаемость.** События аудита и вызовы агентов образуют основу для KPI и панели оценки агентов.

## 3. Модели взаимодействия агентов

| Модель | Когда применяется | Пример |
|---|---|---|
| Агент → код → человек | шаг требует расчёта и обязательства | расчёт цены и объёма в черновике КП, подтверждение продавцом |
| Агент → агент | нужно соединить разбор текста с объяснением результата | агент требований формирует факты, агент предложения объясняет соответствие |
| Агент → сервис → агент | нужен внешний расчёт между вызовами модели | подбор → оптимизатор → объяснение варианта |
| Человек → система | решение, которое нельзя делегировать | допуск документа, выбор предложения, подтверждение резерва |

Правило маршрутизации: модель вызывается только там, где нужен разбор неструктурированного текста или объяснение; расчёты и проверки выполняются обычным кодом. Это снижает стоимость, ускоряет ответ и делает результат проверяемым.

## 4. Безопасность и доверенная среда

- Единая точка выхода к модели: локальная модель вызывается только через `llm-gateway`; внешние маршруты отключаемы, ключи не хранятся в репозитории.
- Обезличивание контекста: в модель уходят «Покупатель B», «Производитель A», «товар категории X» без контактов и реквизитов.
- Разграничение доступа: права проверяются по членству в компании (`auth.company_members`), администратор площадки — отдельный признак.
- Контроль действий: Human Approval Guard и хеш-цепочка журнала решений.
- Ограничение поверхности: сервисы слушают `127.0.0.1`, наружу открыт только edge; секреты обязательны и проверяются при старте.
- Зависимости фиксируются по хешам (`requirements.lock`), что защищает сборку от подмены пакетов.

## 5. Масштабируемость

| Направление | Как обеспечено сейчас | Что требуется на следующем шаге |
|---|---|---|
| Сервисы | независимые процессы, общий Postgres по схемам, обмен по HTTP | вынести оптимизатор и LLM Gateway в отдельные пулы, ввести очередь задач |
| Агенты | типы задач с фиксированными исполнителями, журнал вызовов | добавить параллельную обработку задач и лимиты на компанию |
| Данные | индексы по категориям, статусам и журналам | партиционирование журналов по времени, ретеншен |
| Модель | локальный инференс с отключаемым внешним маршрутом | пул моделей и маршрутизация по стоимости и качеству |
| Пользователи | роли покупателя, продавца, администратора компании и площадки | корпоративные SSO и тонкие права по операциям |

## 6. Обоснование технологий

- **FastAPI и SQLAlchemy 2.0 async** — единый стиль сервисов, явные Pydantic-схемы API и версионирование контрактов.
- **OR-Tools** — детерминированные расчёты объединения и устойчивости вместо «арифметики в модели».
- **Локальная LLM через LLM Gateway** — контроль стоимости и отсутствие передачи клиентских данных наружу по умолчанию.
- **Next.js** — один интерфейс для покупателя и продавца с переключателем режимов без дублирования аккаунта.
- **Postgres и MinIO** — транзакционные данные и файлы документов/изображений в локальном контуре.

## 7. Интеграции

В прототипе внешних интеграций с данными нет: используются синтетические данные. Планируемые направления описаны как следующий шаг, а не как готовая функция:

- реестры юридических лиц и проверка документов;
- ЭДО для обмена закрывающими документами;
- логистические сервисы для расчёта доставки;
- маркетплейсы и каталоги производителей как источник рыночных ориентиров в разрешённых пределах.
