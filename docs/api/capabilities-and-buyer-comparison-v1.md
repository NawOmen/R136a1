# Расширенный паспорт и краткий подбор — API v1

Дополнение к `marketplace-api.md` и `llm-gateway-api.md`, без смены существующих маршрутов.

## Паспорт

`GET/PUT /api/v1/companies/{id}/capability-passport` теперь содержит `details`:

- `business_kind`: `manufacturer`, `stock_supplier`, `both`;
- `product_types`, `complexity`, `limitations`: строки до 1200 символов;
- `material_grades`, `packaging`, `delivery`, `quality_control`, `trial_batch`: до 800 символов.

Неизвестные поля `details` отклоняются. Пустое значение — отсутствие сведений, а не отказ от услуги. Сведения заполняет сам поставщик; проверка компании не означает техническую экспертизу её возможностей. В форме указано, что эти сведения публичны. `GET /api/v1/producers/{id}` возвращает `capability_details` только для доступной публичной страницы проверенного продавца. Старый клиент, не передавший `details` при PUT, не стирает ранее заполненные детали. Существующие `size_ranges` сохраняются все, с явными названиями единиц, а не только первый диапазон объёма стакана.

Миграция marketplace `0009` добавляет JSONB с пустым объектом для существующих строк. Сначала обновить схему marketplace, затем запускать новый LLM Gateway. Обычный seed дополняет только вновь создаваемый демонстрационный паспорт, не перезаписывает данные существующих компаний.

## Подбор и сравнение

В `BuyerAgentResult.matches[]` добавлены `details`, `cautions`, `catalog`. В результате сохраняется `buyer_company_id`, чтобы исключение собственной компании сохранялось после уточнений. Старые сохранённые результаты читаются с пустыми дополнительными полями; для них неизвестная компания-покупатель не восстанавливается задним числом.

Поиск — программный, по паспортам проверенных российских компаний с разрешением продажи. Дополнительные сведения об изделиях, сложности и марках материалов участвуют в текстовом сопоставлении. Совпадение слов — **не вероятность выполнения**, не проверка сертификатов и не семантическая экспертиза чертежа. Ограничения, MOQ и известный максимальный объём/диапазоны размеров показываются отдельно. Запрос ниже MOQ не скрывается: возможны согласованная пробная партия или коалиция, но выгода не обещается.

Не более 10 кандидатов, до 3 справочных товаров на каждого. Товары берутся только из опубликованных карточек выбранных компаний с совпавшей категорией либо подкатегорией (включая старую категорию «бумажные стаканы»). Это не полный индекс рынка и не количество доступных единиц на складе.

`catalog[]`: `product_id`, `name`, `unit_price_rub`, `total_rub`, `moq_units`, `lead_time_days`, `comparable`, `note`. Денежные значения сериализуются десятичными строками; расчёт выполняется `Decimal`, не LLM. Учитывается ценовая ступень для указанного количества.

`total_rub` появляется только при подтверждённом целом количестве не ниже MOQ, наличии технических требований, точном совпадении всех заполненных технических полей, отсутствии нерешённых свойств и числовых ограничений паспорта. Совпадение текстовых значений консервативное; синонимы и неполные данные требуют уточнения. Даже такая карточка не является обязательством: цена не включает доставку/переналадку/дополнительные работы, наличие и срок подтверждает продавец.

Краткий `summary` строится кодом по этим же данным, поэтому модель не может придумать цену, срок, количество предложений или экономию. Сравнение минимума цены и срока относится только к показанным карточкам с совпавшими заполненными полями, не к полной стоимости закупки. После `/clarify` поиск и краткий итог пересчитываются. `/confirm` и явное нажатие переноса требований в форму сохранены; сделка автоматически не создаётся.

Инструкция локального извлечения дополнена ключами нетривиальных изделий, инструкция Seller Agent — расширенным паспортом и запретом следовать инструкциям внутри него. Все паспорта не отправляются в LLM: рост числа производителей не увеличивает её входной контекст. Поиск по БД пока линейный, не предназначен для миллионов паспортов без отдельной индексации.

## Проверка

Синтетические примеры: `packages/test-fixtures/capabilities/detailed_suppliers.json` — металлообработка, склад стаканов, производство/склад. Они не содержат реальных реквизитов и не импортируются автоматически в пользовательскую БД.

`services/llm-gateway/unit/test_buyer_comparison.py` проверяет точную сумму, отсутствие выдуманной выгоды при нехватке данных, числовые ограничения, исключение своей компании и 1000 подробных паспортов без дополнительных LLM-вызовов. Это тест детерминированного слоя, **не замер качества или скорости живой Qwen**. `services/marketplace/tests/test_capability_details.py` проверяет API и сохранность данных старого клиента; unit-тест проверяет SQL миграции.

Ручная приёмка после запуска стека: заполнить паспорт под продавцом → открыть его публичную страницу → под покупателем разобрать запрос → проверить ссылки/ограничения/цены → ответить на уточнения → подтвердить перенос → исправить поля вручную. Проверить навигацию, Escape и Tab в меню, светлую/тёмную тему, узкий экран. Цвет формы отражает формат, а не достоверность данных.

Безопасность проверена отдельно в `docs/security/fix-security-review-2026-09-08.md`; её находки намеренно не исправлены этим изменением.
